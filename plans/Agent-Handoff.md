## Critical Context: The Questionnaire Has 10 Questions, Not 16

**Why this matters:** Product.md specced a 16-question, 4-stage assessment flow. That flow was never fully built. The live UI has exactly **10 questions** (steps 0–9 in `components/exitiq/ExitIQApp.tsx`). An earlier agent session was generating code based on the full 16-question spec, producing incorrect scoring logic and wrong signal assumptions. Every agent must anchor to the 10 live answers, not the Product.md schema.

**The 10 live answer keys** (defined in `lib/exitiq/data.ts` as `ANSWER_KEYS`):
`industry`, `years`, `facilityType`, `revenue`, `sde`, `docReadiness`, `customerConc`, `employees`, `keyMan`, `recurringRev`

**How they map to the DB schema:**
- 7 go directly into `stage1`: `industry`, `years`, `revenue`, `sde`, `employees`, `facilityType`, `docReadiness`
- 3 are translated from UI slugs into `stage2`/`stage3` by the Signal Mapping Fix (Session 1):
  - `customerConc` → `stage2.customerConcentration`
  - `recurringRev` → `stage2.recurringRevenue`
  - `keyMan` → `stage3.keyPersonRisk`

**All other `stage2`, `stage3`, and `stage4` fields are always `null`.** The schema defines them because Product.md planned them; the UI never collected them. Do not confuse "schema supports 4 stages" with "4 stages are answered."

## What the System Is

exitIQ is an AI-powered exit assessment tool for small business sellers (deals under $10M). A seller completes 10 questions, sees a pre-gate teaser valuation, provides contact info, and receives a full "Exit IQ Report." The report has two layers:

1. **Visual/card sections** — quantitative outputs computed by deterministic math models (scores, valuation ranges, SBA figures, etc.)
2. **Narrative prose sections** — qualitative advisor commentary generated by Claude Sonnet, rendered inside each visual card

The report is rendered at `app/report/[sessionId]/page.tsx` using data from `buildReportData()` and narrative from `reportMd` stored in the database.

## The Problem This Refactor Solved

Before these sessions, the report pipeline had five distinct bugs:

**Bug 1 — Math models and LLM used different inputs.**
`buildReportData()` (math model) and `buildReportPrompt()` (LLM prompt) each independently called `computeScore`, `getValuationRange`, and `computeSBASnapshot`. If their inputs differed by even one field, the LLM narrative would cite different numbers than the visual cards showed.

**Bug 2 — Stage 2/3 signals were never reaching the math models.**
`customerConc`, `recurringRev`, and `keyMan` (3 of the 10 answers) were being packed into the `stage1` JSONB column under the wrong field names, with the wrong slug values. The scoring model never saw them. Customer concentration detractors, recurring revenue drivers, and key-person-risk dimension scoring were all falling through to neutral defaults for every user.

**Bug 3 — The LLM output was silently discarded.**
`FullReportVisual` accepted `reportMd` as `_reportMd` (TypeScript "intentionally unused" convention). Every user saw only the math-model visual cards. The Sonnet-generated narrative — billed per call, personalized per seller — was never rendered.

**Bug 4 — The LLM section headers didn't match the visual section labels.**
`report-visual.tsx` used `SectionLabel` strings (e.g., `"SBA 7(a) Eligibility"`) while the LLM prompt instructed the model to use different headers (e.g., `"SBA Eligibility Assessment"`). The `parseNarrativeSections` parser keyed on exact header strings, so the mapping always failed — even if the LLM output was wired in, it would have been placed in the wrong sections.

**Bug 5 — The loader could strand users permanently.**
If the AI stream failed (network error, server error), `reportStreaming` went to `false` and `reportMd` stayed `""`. `aiReady` evaluated to `false`. The `CinematicLoader` stuck at 99% with no timeout, no error state, no fallback — the user was permanently stranded.

## The Refactored Pipeline: How It Works Now

### Step 1 — 10-Question Questionnaire (pre-gate)
`components/exitiq/ExitIQApp.tsx`, steps 0–9. Answers saved to `localStorage`. No API calls at this stage.

### Step 2 — Pre-Gate Teaser
After question 9, `GateTeaserCard` renders from `components/exitiq/preview.tsx`. Shows a valuation range, exit readiness score, and grade. All computed **client-side** by `calcDerived(answers)` from `lib/exitiq/calculations.ts` — pure math, no API call.

The teaser valuation is computed using `computeSdeMultiple()`, which adjusts the industry SDE multiple based on individual signals (customerConc, keyMan, recurringRev, docReadiness, facilityType, years).

### Step 3 — Email Gate
`EmailGateModal` collects first name, email, and selling timeline. On submit, `handleSubmit` fires.

### Step 4 — Session Persistence + Report Generation
`handleSubmit` runs two things in sequence:

**4a. `persistSession()` → `POST /api/assessment/session`**
Writes to DB:
- `stage1`: industry, years, revenue, sde, employees, facilityType, docReadiness
- `stage2`: customerConcentration, recurringRevenue (translated from UI slugs)
- `stage3`: keyPersonRisk (translated from UI slug)
- `gate`: firstName, email, sellingTimeline, segmentTag

**4b. `requestGenerate()` → `POST /api/assessment/generate`**
Server-side flow (in `app/api/assessment/generate/route.ts`):
1. Calls `mapStage1ForScoring(stage1)` — translates human labels to scoring slugs
2. Calls `buildReportData(s1Scored, firstName, timeline, stage2, stage3, stage4)` **once** — produces the frozen `ReportData` object
3. Passes that frozen `ReportData` to `buildReportPrompt(session, reportData)` — the prompt reads all quantitative values from `reportData`, recomputes nothing
4. Streams Sonnet response back to client
5. After stream closes: saves `reportMd` to `assessment_reports` via Next.js `after()`

**The single-computation guarantee:** `buildReportData` is called exactly once per generation. The LLM prompt and the visual renderer share the same frozen numbers. Divergence between prose and charts is structurally impossible.

### Step 5 — CinematicLoader
`CinematicLoader` from `components/exitiq/report.tsx` runs for the duration of AI generation (~20–40s). It has two completion triggers:
- **Normal path:** `phasesComplete && aiReady` — fires when the 42s phase animation finishes AND the stream closes with non-empty `reportMd`
- **Fallback path:** A `useEffect` unconditionally calls `onComplete()` after 90 seconds — prevents permanent stranding if the stream fails

### Step 6 — Report Page
`app/report/[sessionId]/page.tsx` (server component):
1. Fetches session + report from DB in parallel
2. Calls `mapStage1ForScoring(stage1)` — same slug translation as the generate route
3. Calls `buildReportData(s1Scored, firstName, timeline, stage2, stage3, stage4)` — produces `ReportData` for the visual
4. Renders `<FullReportVisual data={data} reportMd={report?.reportMd ?? undefined} />`

`FullReportVisual` in `components/exitiq/report-visual.tsx`:
- Calls `parseNarrativeSections(reportMd)` — splits on `\n## ` headers, returns `Record<string, string>`
- Distributes prose sections to their matching visual components by exact header string
- Each section renders math-model cards at top, then `NarrativeProse` at bottom
- `NarrativeProse` always renders (never `null`) — shows either real prose or an italic "Analysis not available" placeholder

### Signal Mapping Fix — Pre-Gate Signals Stored in Wrong Stage

**Files changed:** `components/exitiq/ExitIQApp.tsx`, `app/api/assessment/generate/route.ts`

**What changed and why:**
`customerConc`, `keyMan`, and `recurringRev` were being written into the `stage1` JSONB column using a TypeScript `as` cast to suppress the type error. - Added `stage2` and `stage3` as top-level fields in the `persistSession()` call

**Fix in `app/api/assessment/generate/route.ts`:**
- Added stale-cache detection: if `session.stage2.customerConcentration` is present (new signal mapping) AND the cached report predates `2026-05-12T00:00:00Z` (the fix deployment date), bypass cache and regenerate

### Mini-Prompt 8 — Bridge Pre-Gate and Post-Gate Valuation Numbers

**Files changed:** `lib/assessment/report-transform.ts`, `lib/ai/prompts.ts`

**What changed and why:**
The pre-gate teaser shows a valuation range computed by `calcDerived()` using `computeSdeMultiple()` — an adjusted multiple based on individual signals (customerConc, keyMan, recurringRev, docReadiness, facilityType, years). The post-gate full report shows a different range computed by `getValuationRange()` — the raw industry SDE multiple range averaged with the revenue multiple. A user who sees "$800K–$1.4M" in the teaser and "$650K–$950K" in the full report with no explanation loses trust.

The fix has two parts: make the pre-gate estimate available in the report context as a locked math-model value, and instruct the LLM to open the Valuation Analysis section with one bridge sentence that cites the pre-gate number and names the specific signals that explain why buyers will anchor toward the low end.

**`lib/assessment/report-transform.ts`:**
- Added `getTeaserRange` to imports from `@/lib/assessment/scoring`
- Added `teaserValuation: { lo: number; hi: number; bridgeNote: string }` to the `ReportData` interface
- Added `buildTeaserBridgeNote(detractors, s1, s2): string` helper — reads the detractors array and scored stage1/2 signals to produce a concrete phrase (e.g., `"high customer concentration and owner-dependent operations"`). Checks: `s2.customerConcentration === "over_50"` → "high customer concentration"; presence of an Operational Independence detractor → "owner-dependent operations"; `s1.docReadiness === "fair" | "poor"` → "incomplete financial documentation". Falls back to `"the full assessment scoring all collected signals"` if no signals fire.
- In `buildReportData()`: calls `getTeaserRange(s1Scored)` (the `getValuationRange` range widened ±25%) and `buildTeaserBridgeNote()` after detractors are computed; returns `teaserValuation` in the struct

**`lib/ai/prompts.ts`:**
- Removed stale `getTeaserRange` import (was imported but unused; the value now comes from `reportData`)
- Destructured `teaserValuation` from `reportData`
- Added `TEASER_LO`, `TEASER_HI`, `TEASER_SIGNALS` to the LOCKED VARIABLE REGISTRY (all frozen — model cannot alter them)
- Updated `## Valuation Analysis` writing instruction: "Open with exactly one bridge sentence that: (a) names the pre-gate estimate TEASER_LO–TEASER_HI the seller already saw, (b) states the refined analysis range VALUATION_LO–VALUATION_HI, and (c) cites TEASER_SIGNALS as the factor(s) that explain why buyers will anchor toward VALUATION_LO rather than VALUATION_HI."

**Why the teaser and report ranges differ structurally:**
- Teaser (`calcDerived` / `computeSdeMultiple`): adjusted SDE multiple × SDE mid. The multiple moves up/down based on signals.
- Report (`getValuationRange`): average of (raw industry SDE range × SDE mid) and (raw revenue multiple × rev mid), floored at 25% of revenue. No signal adjustment.
- `getTeaserRange` = `getValuationRange` ± 25% — always wider than the report range by construction. This is intentional: the pre-gate estimate is a conservative wide band; the report is the refined, methodology-grounded range.

### LLM Prompt Structure

The LLM receives:
1. **ABSOLUTE PROHIBITION** — forbidden from computing, estimating, or inventing any number
2. **LOCKED VARIABLE REGISTRY** — every quantitative value as a named constant, including `TEASER_LO`, `TEASER_HI`, `TEASER_SIGNALS`
3. **SELLER'S QUALITATIVE ANSWERS** — human-readable labels for context only (not numbers)
4. **WRITING INSTRUCTIONS** — exact section headers, section-specific guidance

The LLM must produce exactly 9 sections with these exact `##` headers:
`## Executive Summary` · `## Valuation Analysis` · `## SBA 7(a) Eligibility` · `## Transferability Score` · `## Value Drivers` · `## Value Detractors` · `## Recommended Deal Structure` · `## Growth Levers` · `## Next Steps`
