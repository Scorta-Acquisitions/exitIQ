## Three Scorta premises — verification with citations

**Premise 1 — Clerk<->Supabase third-party auth (Clerk JWT + Supabase RLS) is currently first-class.**
YES, current and first-class. The canonical Supabase docs page is https://supabase.com/docs/guides/auth/third-party/clerk; the overview hub is https://supabase.com/docs/guides/auth/third-party/overview (renders today, 2026-09-02). Verbatim wording: "Clerk can be used as a third-party authentication provider alongside Supabase Auth, or standalone, with your Supabase project" [three_scorta_premises_verification_with_citations_no_advice[0]] [34]. Setup steps are explicit: (1) configure Clerk session tokens w/ `role` claim, (2) add a Third-Party Auth integration w/ Clerk via the Supabase dashboard, (3) configure `supabase/config.toml` w/ `[auth.third_party.clerk] enabled = true` plus `domain = "example.clerk.accounts.dev"`, (4) set the Supabase client `accessToken` callback to `Clerk.sessionToken().jwt` in TypeScript/Flutter/Swift [three_scorta_premises_verification_with_citations_no_advice[0]] [34]. RLS section states: "you can use RLS policies to secure access to your project's database, Storage objects and Realtime channels." The recommended pattern uses JWT claims directly in `create policy` predicates (e.g., checking the Clerk `organization_id` claim and requiring `org:admin`) [three_scorta_premises_verification_with_citations_no_advice[0]] [34]. The OLDER JWT-templating path is explicitly deprecated: "As of 1st April 2025 the previously available Clerk Integration with Supabase is considered deprecated and is no longer recommended for use"; "All projects using the deprecated integration will be excluded from Third-Party Monthly Active User (TP-MAU) charges until at least 1st January 2026" [three_scorta_premises_verification_with_citations_no_advice[0]] [34]. Net: Clerk + Supabase is a live, documented, first-party integration as of 2026-09-02; do NOT use the JWT-template path — use the native Third-Party Auth add-in.

**Premise 2 — File layer swap to AWS S3 (+KMS/CloudTrail) in days, not a rewrite.**
Mixed per kit, evidence-backed:
- MakerKit Lite / MakerKit full (Supabase Storage default): Realtively close to a swap, because Supabase Storage exposes an S3-compatible endpoint (https://supabase.com/docs/guides/storage/s3/authentication). Two auth paths documented: (1) S3 access keys generated in project settings (server-side only), (2) Session Token + RLS (user-scoped). KMS/CloudTrail then live entirely on the AWS side and are not baked into the adapter [three_scorta_premises_verification_with_citations_no_advice[1]] [32]. Therefore for MakerKit: realistic to swap by repointing bucket names + adapting callsites, then layering KMS/CloudTrail locally in AWS — days-scale, not a rewrite.
- vercel/next-forge: NOT close to a swap. `packages/storage/package.json` declares only `@vercel/blob` as the storage dependency; there is no S3 adapter, Files-SDK wrapper, or conditional provider in the shipped code. Replacing it requires a code rewrite of callsites.
- ixartz SaaS-Boilerplate & ixartz Next-js-Boilerplate: No shipped file/storage layer at all (SaaS-Boilerplate `src/libs` contains only DB, Env, I18n, Logger [three_scorta_premises_verification_with_citations_no_advice[2]] [11]; Next-js-Boilerplate has no storage module either [three_scorta_premises_verification_with_citations_no_advice[3]] [15]). There is no surface to swap — anything would be net-new.

**Premise 3 — Kit avoids requiring a SECOND database or SECOND auth system to function.**
Mostly satisfied, with one caveat:
- MakerKit Lite AND MakerKit full (Supabase Auth + Supabase Postgres + Supabase Storage) use ONE auth + ONE DB (do not depend on Clerk) [three_scorta_premises_verification_with_citations_no_advice[4]] [29][three_scorta_premises_verification_with_citations_no_advice[5]] [28]. Premise holds.
- vercel/next-forge: ONE DB (Prisma+Postgres) but uses Clerk as auth. With the Supabase Clerk third-party-auth path documented [three_scorta_premises_verification_with_citations_no_advice[0]] [34], a single-DB-then-add-Supabase path exists IF next-forge's Postgres becomes Supabase Postgres — but next-forge currently pairs Clerk with Neon adapter via Prisma, not Supabase. Adding Supabase later would mean adding Supabase Auth alongside Clerk, which violates "one auth system" momentarily. Premise does not hold as-shipped today.
- ixartz SaaS-Boilerplate & ixartz Next-js-Boilerplate: One DB each (PostgreSQL via PGlite/Drizzle) [three_scorta_premises_verification_with_citations_no_advice[6]] [14]; auth = Clerk only. If Clerk is swapped to Supabase Auth (or vice-versa) the existing schema is too thin to support per-tenant RLS out of the box (only `todo` and `counter` tables) [three_scorta_premises_verification_with_citations_no_advice[7]] [9][three_scorta_premises_verification_with_citations_no_advice[8]] [16]. Premise holds structurally; whether the kit can actually run Supabase RLS without further schema work is UNVERIFIED.
